# 资产库维护缺陷模式与处置（症状 → 根因 → 命令级步骤）

## 适用场景（When to Use）

- 维护多文件 markdown 资产集/知识库/SOP 库/configuration-as-document 体系
- 重构、合并角色、去品牌化改写、批量重命名等大改动之后
- 症状样例：「两个权威文件对同一数值说法不一」「check 说完成但产物时间戳是旧的」「文档引用的实体 Grep 不到」「成文规则要求填的字段全库为空」

## 快速判定：症状 → 根因映射

| 症状特征 | 根因类型 | 处置分节 |
|---|---|---|
| 两份文档对同一数值/规则说法不一 | 契约冲突·权威源指向死循环（A→B→C 而 C 无此项） | §步骤 1 |
| 对账/检查判"完成"，但产物是旧一轮的 | 存在性锚点被旧产物冒充（缺时间维度） | §步骤 2 |
| 重构/合并角色后，引用找不到定义 | 知识漂移随重构自发生成（退役实体名残留） | §步骤 3 |
| 成文规则要求的字段/文件，全库都不存在 | 规则与资产矛盾态（既不补齐也不声明豁免） | §步骤 4 |
| 注记写"后续版本将修"，修完没人回填 | 实施注记未随实施闭环 | §步骤 5 |

## 标准处置步骤

1. **权威源闭环检查**：对每个被引用的数值/规则 Grep 全库（`grep -rn "<数值或规则关键词>" <资产根>`），列出全部出现位置；沿"谁指向谁"画指向链——链尾没有定义处即死循环。修复：在链尾补定义（一处），其余位置改纯引用（删数字只留指路）；若数值属不同类别（如运行类 vs 索引类），显式分治并各自指定唯一权威位
2. **完成判定加时间维度**：任何"文件存在=完成"的判定，补比对产物 mtime 与登记时间戳（`stat <产物>` / `os.path.getmtime`）——产物早于本次登记即旧产物残留，报"STALE"而非"OK"；重派任务时尤其必查
3. **重构后退役实体扫描**：合并/删除/改名任何角色或文件后，Grep 全库旧名（`grep -rn "<退役实体名>" <资产根>`）——非零命中逐条改指现役名。此扫描应固化为重构战役收官清单的固定项（重构不产生漂移的唯一保证）
4. **规则-资产矛盾消解**：发现"规则要求 X 而全库无 X"时二选一，不允许并存：补齐资产（按规则做）或在规则处显式声明豁免范围。检查命令：对规则的每个"不可缺/必须"字段 Grep 目标形态（如 `grep -rn "^元信息：" --include="*.md"` 对元信息块）
5. **注记回填闭环**：含"后续/以后/待办"字样的注记（`grep -rn "后续版本\|待办\|以后修" <资产根>`），在对应实施完成时于原注记处追加一行"YYYY-MM-DD 已完成（战役/提交锚）"——不删除原注记（时间戳快照有历史价值），只追加闭环记录

## 禁止事项（红线）

- 权威数值双写"图方便"——一处改了另一处必漂移，活案例：18 vs 10 行数上限不一致翻车（2026-10 自审实测）
- 旧产物直接当本轮成果用——回炉场景静默死亡被"成功"覆盖（判例：首轮 FAIL 报告残留致 check 误报 OK）
- 重构收官不跑退役实体扫描——知识漂移必然发生（判例：data-exp 实体名在合并进子模式后仍被判例引用）

## 先例引用（provenance）

- 2026-10-02 重构战役（git: b11c937..38a5973）：data-exp 退役实体残留、"v1.1 转化注记"未随 v1.0 实施回填——两项在终验中被机械扫描抓获
- 2026-10-01：元信息块"规则说不可缺而四个 SKILL.md 全缺"——矛盾态实例，走"补齐资产"路线消解

## 验证清单（Definition of Done）

- [ ] 全库 Grep 任一权威数值，定义处唯一
- [ ] "存在即完成"类判定全部含时间维度比对
- [ ] 最近一次重构之后的退役实体名为零命中
- [ ] "不可缺"类规则的每个字段在资产中实存（或有显式豁免声明）
- [ ] 全部"后续将修"注记要么未到期、要么已回填闭环记录
