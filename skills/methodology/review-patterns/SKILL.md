# 审查缺陷模式库（五类反模式核查 + 审查五法）

## 适用场景（When to Use）

- 方案设计后自审（预判清单——把审查缺陷前置到设计侧，配合 design-lessons）
- 对抗审查 / 红线域守卫执行中的技巧参考
- 验证断言设计（真断言 vs 冒烟）

## 五类缺陷模式（发现即拦）

| 模式 | 特征 | 核查方法 | 拦截案例（示例） |
|---|---|---|---|
| 知识漂移型 | 方案/文档引用已退役/更名实体 | 设计前 Grep 实存清单（agents/表/函数） | 实例：方案引用当天退役的 agent 定义——「方案治的就是知识漂移，自身却引入了一次漂移」 |
| 静默失败型 | rc=0 / 退出码 0 但副作用未发生 | 核对副作用本体（DB 行/文件/日志），不信 rc 回声 | 实例：工具判 PASS 但目标操作被风控类机制拦截、零真实生效——断言必失败且与审计链不符 |
| 审计断链型 | 人工干预无留痕，事后与自动行为不可区分 | 检查审计记录三字段（reason/triggered_by/created_at）齐备 | — |
| 契约冲突型 | 两份权威文件对同一对象矛盾指令 | 交叉 Grep 同一对象的所有权威定义点 | 实例：总索引与主指令文件对同一路由节各行数上限不一致（18 vs 10） |
| 窗口期风险型 | draft/半配状态可被提前消费 | description 首句内置门禁 + 状态机推演（谁可能在此窗口读它） | — |

各领域使用时：把「拦截案例」列逐步替换为本项目实证（保留 1-2 条示例均可，替换不删列——空案例列会让模式退化成理论）。

## 审查五法（怎么查出来）

1. **先立后破**：先实证核实方案做对的部分（逐项 Grep/行号复核成表），全部成立后才开审查发现——防对抗审查变全盘否定
2. **自反一致性**：方案手段与方案批判的目标是否自相矛盾（例：批判「主指令文件膨胀」的方案自己设计数百行呈报内容直灌主文件；批判「依赖自觉」的触发规则自身依赖某人自觉执行）
3. **并发写者排查**：找「另一个写入方」及其触发时序（同一资源谁还会写？什么条件触发？两条写路径会不会相遇）
4. **旁证反查**：用生产/运行数据反推拦截是否真实发生（例：目标链路日产出 0 行 = 确被某门禁拦截的实证，而非巧合）
5. **独立实证**：不采信实施报告自述；diff hunk 数比逐条断言更强（例：「git diff 仅 1 个 hunk」直接推翻「逐文件改过 12 处」的自述）

## 验证断言附则（验证质量决定项）

- **真断言 vs 冒烟**：断言实质行为（如「目标记录数=N 且持续 M 个周期」）而非只跑通（exit 0）
- **零越界核查**：`git status` 改动面穷举 = 规格外文件为零
- **schema 漂移专项**（适用于一切用 SQL/强 schema 的项目）：手写 SQL 的列名/主键漂移——发现一处 → **全库同型 Grep**（同类问题必然成族）；修好 JOIN 键要预期连环炸出第二层；**勿信「测试通过」**（测试可能跑的是旧 schema 快照）

## 度量系统校准附则

检测器/告警/门禁上线前：先用**已知阴性样本**定基线（正常情况下它报不报），再用**已知阳性样本**验功效（异常情况下它报不报）——两步都过才可信。判「零损失/零告警」前先确认检测器本身活着。

## 禁止事项（红线）

- 审查只列发现不做先立后破（全盘否定风险）
- 采信实施报告自述作为唯一证据
