# 四模板全文（收官提炼路由用；按来源类型机械路由，不做主观判断）

> 版本 v1.0
> 模板按知识的「诞生场景」分类——任何领域的经验都诞生于这四种场景之一，字段名全为中性词，模板即通用版。

## 路由表

| 来源特征 | 模板 | 核心字段 |
|---|---|---|
| 实施报告 / 修复判例 | 模板一·修复 | 症状 / 根因 / 步骤 / 先例 |
| 方案选型节 / 非目标节 | 模板二·设计 | 决策 / 备选与排除理由 / 适用边界 |
| 审查报告 High/Medium 发现 | 模板三·审查 | 缺陷模式 / 发现方法 / 拦截案例 / 适用场景 |
| 根因反转 / 排除逻辑结论 | 模板四·认知 | 先验假设 / 证伪证据 / 修正结论 / 方法论 |

多来源材料按**主导模板**计一次（不重复计数）；references 可跨 skill 多挂。

## 模板一·修复类（最全模板，六节）

```markdown
---
name: <前缀>-<模式名>
description: "<何时用：具体症状特征，含错误码/表名/行为样例>"
---
# <标题>

## 适用场景（When to Use）
- <症状样例 2-4 条，含真实错误信息原文——"rc=0 但 0 行导入"比"假成功"可检索得多>

## 快速判定：症状 → 根因映射
| 症状特征 | 根因类型 | 处置分节 |
|---|---|---|
| ... | ... | §步骤 N |

## 标准处置步骤
1. <编号步骤，每步含具体命令/SQL/判定条件——可执行，非原则陈述>

## 禁止事项（红线）
- <每条附违例后果，引用真实事故——红线不配事故案例就没有说服力>

## 先例引用（provenance）
- <版本号 / 战役报告路径 + 一句话结论>

## 验证清单（Definition of Done）
- [ ] <可观测的完成判据>

---
元信息：状态=<active|draft|stale> ｜ 最后验证=<YY-MM-DD> ｜ 适用版本=<...> ｜ 源材料=<路径>
```

设计精髓：①症状→根因映射表把诊断从「通读全文」变成「查表」；②步骤必须可执行（命令级，不是「注意检查」级）；③红线必须配真实事故引用。

## 模板二·设计类（选型理由与排除论证——防决策回锅）

```markdown
---
name: <前缀>-<主题名>
description: "<何时用：设计场景特征（选型论证/非目标划定/回滚设计等）>"
---
# <标题>

## 决策（What）
- <做了什么选型决策，一句话可复述>

## 备选与排除理由（Options & Why Not）
| 备选 | 结论 | 排除理由（证据锚/判例/成本论证） |
|---|---|---|
| A | 采用 | — |
| B | 排除 | <依据> |

## 适用边界（Boundary）
- <什么条件下本决策有效 / 何时应重新评估>

## 先例引用（provenance）
- <方案文档路径 + 一句话结论>

---
元信息：状态=<active|draft|stale> ｜ 最后验证=<YY-MM-DD> ｜ 适用版本=<...> ｜ 源材料=<路径>
```

设计精髓：核心是**防决策回锅**——每个「不做 X」必须附排除理由+证据锚，否则每个新 session 重新论证一遍（调研成本重复支付）；「适用边界」让决策知识自带保质期。

## 模板三·审查类（缺陷模式与审查技巧）

```markdown
---
name: <前缀>-<主题名>
description: "<何时用：审查/核查场景特征（方案评审/门禁设计/断言设计等）>"
---
# <标题>

## 缺陷模式（Pattern）
- <可命名的反模式，一句话——可 grep、可引用>

## 发现方法（How Found）
- <怎么查出来的：技巧 / 推理链 / 检查命令——可复制>

## 拦截案例（Case）
- <真实拦截实证：报告路径 + 拦截结果——防模式被当成理论空谈>

## 适用场景（When）
- <什么类型的方案 / 代码 / 流程会出现此模式>

---
元信息：状态=<active|draft|stale> ｜ 最后验证=<YY-MM-DD> ｜ 适用版本=<...> ｜ 源材料=<路径>
```

设计精髓：**缺陷模式可命名化**——把一次审查拦截转化为可复用的三件东西：模式名（可检索）、发现方法（可复制）、拦截案例（实证）。

## 模板四·认知类（根因反转与排除逻辑——即时通道主用）

```markdown
---
name: <前缀>-<主题名>
description: "<何时用：定性修正/排除验证场景特征>"
---
# <标题>

## 先验假设（Prior）
- <当时的定性 / 假设及其依据>

## 证伪证据（Evidence）
- <推翻假设的实证（文件:行号 / 数据 / 隔离实验）>

## 修正结论（Revised）
- <修正后的定性及影响面>

## 方法论（Method）
- <可复述的排除 / 验证步骤>

---
元信息：状态=<active|draft|stale> ｜ 最后验证=<YY-MM-DD> ｜ 适用版本=<...> ｜ 源材料=<路径>
```

设计精髓：**保存推理结构而非结论**——四字段记录的是「思维怎么转弯的」。反转时刻的推理结构事后重建必然失真，所以必须当场落盘（origin=reversal 即时通道的主用模板）。

## 四模板共通规则

1. 正文行数上限为硬约束（数值以知识库总索引维护规则为唯一权威），超限往 references/ 拆
2. 元信息块四类同构（状态/最后验证/适用版本/源材料）——保证总索引可按统一列聚合、可排序、可做过期扫描；**draft/stale 状态条目的 description 首句必须内置状态警告（如「draft——未采纳，仅供参考」）——状态警告放在最先被读到的位置，防 Grep 兜底检索的窗口期消费**
3. 修复类固定含「禁止事项 / 验证清单」两节；模板二三四按需内嵌等价节（设计类的「适用边界」即红线等价物）
4. **模板选择按来源类型机械路由，不允许跨类混填**——这是提炼 agent 可安全执行的边界

## 判例引用通用红线

- 判例引用必须带可回溯锚（日期 / 报告路径 / 版本），裸结论不收
- 示例判例若来自其他项目，标注「实例来源：<项目名>」
