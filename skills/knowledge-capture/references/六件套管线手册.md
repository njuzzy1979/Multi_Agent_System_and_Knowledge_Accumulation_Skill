# 六件套管线手册（编排者必读）

> 版本 v1.1

## 0. 术语表（全文按此口径）

| 术语 | 含义 |
|---|---|
| 战役 | 一次有编排的多阶段工作单元（从侦查/设计到收官归档）；重型走全链，轻量按 §1 选轨降阶 |
| 档位 | agent 的模型档位分轻/重两档：轻≈标准档（如 sonnet），重≈旗舰档（如 opus）；映射由编排器按项目平台对号 |
| 收官 | 战役末段收口：对账 check + 文档归档 + 知识提炼判定 + 呈报（见 §8 清单） |
| 机械锚 | 对 LLM 的行为要求配机械可执行的触发器（收到 X 必做动作 Y），不依赖自觉。分两型——READ-DO 型（顺序敏感，须照单逐步执行，如 domain-guard 第 0 步自检）与 DO-CONFIRM 型（战后对照确认，如收官清单）；新增机械锚时显式选型 |
| 落盘即遗忘 | 子 agent 详情 Write 到战役目录、final report 只允许极简三行的输出契约 |
| 回炉 | 门禁 FAIL 后退回上游环节返工（验证首轮 FAIL 属设计内防线，不触发流程告警） |
| 红线域 | 项目自声明的不可妥协域（资金/安全/隐私/生产数据删除/付费计费等），守卫强制插入 |
| expect 产物 | dispatch 时登记的预期产物文件路径；存在即视为完成（对账锚点，不锚自述） |
| 平台字段优先、行为约束兜底 | frontmatter tools/hooks 等平台字段在支持的宿主生效（机械强制），不支持的宿主退回正文行为约定——两者并存不矛盾 |

## 1. 管线总览

```
① 侦查（eng-recon ×N 并行：tech 可行性 / data 数据事实 / research 外部参考 → r1_/r2_ 报告落盘）
② 设计（eng-arch 方案综合；复杂战役才走，小修复可跳过直接进审查）
③ 对抗审查（adversarial-reviewer：默认假设方案有缺陷，用证据说服自己它是对的）
④ 实施（eng-implementer：按单任务规格编码）
⑤ 交叉验证（eng-validator：方案↔diff 逐条对照，MISSING/OVERSTEP/DEVIATION 三分法）
⑥ 归档（eng-documenter：文档同步 + 知识提炼机械路由）
```

**红线域守卫无条件插入**：任何阶段发现改动触碰项目声明的红线域（资金/安全/隐私/生产数据删除/付费计费等）→ 审查环节强制加插 domain-guard，不因「改动量小」而降档。

**按改动重量选轨（四档）**：直通=无行为歧义的微改（typo/注释/格式）不走管线直接改，顺带发现走登记；机械小改=④⑤；轻量（单点修复/配置调整）=③④⑤；重型（跨模块/新机制/动核心数据）=全链。选轨判断由编排者在战役开始时显式声明（写进战役计划，不隐性降轨）。

**侦查子任务预算参考**：tech 子模式、data 子模式、research 子模式各有调用预算上限与超预算动作（数值唯一权威=集成段硬性规则 9，本手册不自报）——超预算按降级路径上报，不继续烧

**测试承接**：管线不设独立测试 agent（test-designer / integration-verifier 两角色因出场痕迹不足被裁——调用痕迹治理判例）。测试执行由**编排器（主对话）承担**——implementer 自查通过后、validator 交叉验证前后，编排器按项目声明的测试命令跑回归；无测试体系的项目以 validator 静态对照为准。

## 2. 编排器语义（六条铁律）

1. **编排是主对话的职能（depth-0），不是可分派的子 agent**。早期设计曾设两个编排器剧本 agent，最终因嵌套委托的工具不可用/降级兜底复杂度被实战退役（git rm），编排职能收归主对话。教训：编排器需持有 Agent 工具与全局上下文，做成子 agent 必然面临嵌套困境。
2. **落盘即遗忘**：子 agent 详情一律 Write 到战役目录（`<报告根>/exec-detail-<战役名>/`）；final report 只允许极简三行（见 §3）。上下文预算是长战役编排者最稀缺资源。
3. **战役级预算**：单 agent 不设名义硬超时（机械任务 2 分钟、深度审查 40 分钟，名义超时必误杀）；按**战役级 token/时长预算**管理，超预算编排器主动终止（TaskStop）。
4. **有限重试 + 熔断上报（分域语义）**：轻环节（侦查 ×N）部分实例失败——保留已成功实例产物、收官呈报显式标注覆盖缺口、可选补派单个实例（不重跑全组）；重环节（审查/验证/守卫）门禁失败按集成段硬性规则 7 的重试上限重试 → 仍失败 → 问题登记 P0 + 停流水线呈用户。杜绝无限重试烧预算和静默吞失败两态。
5. **禁止虚报状态**：真实派发 agent 后才能写进度 RUNNING；状态真实性是编排可信的前提（实战中曾专门立此为记忆级规则）。
6. **战役计划先落盘**：首个 dispatch 之前把战役计划（目标/选轨/agent 清单/expect 产物路径表/预算+状态行区）Write 到 `<战役目录>/campaign.md`——主对话上下文被压缩后据此恢复；每完成一个管线环节机械追加状态行；新 session 接手中断战役的首步动作=Read 该文件，从最后完成环节的下一环继续

## 3. 极简三行制（输出契约）

```
[AGENT-OUTPUT-START] <agent 名>
<关键字段>=<值> | 判定=<PASS|FAIL|DONE|DEGRADED> | 结论=<一句话总结>
报告=<落盘路径>
[AGENT-OUTPUT-END] <agent 名>
```

- 编排器按**判定字段机械路由**：PASS/DONE → 下一环节；FAIL → 回炉；DEGRADED → 人工介入，介入动作四选一：**批准重试**（approve）/ **修正任务书后重派**（edit）/ **否决并归因**（reject，理由回传上游）/ **直接答复替代**（respond）——无需读全文
- 判定行可按需扩展字段（如 documenter 并入 `SOP草稿=<文件名>`），**不增行**
- 演进教训（实战实测）：旧「标记包裹全文」方案失败——标记内全文仍回灌上下文，它解决的是「格式混淆」而非「内容进上下文」；三行制解决后者。**任何输出契约方案先问：内容到底进不进主对话上下文？**

**环境局限诚实声明**：宿主平台无 final message 长度原语时，三行制的最终防线是 agent 自律截断（prompt 约束已是环境内最强手段）；编排器侧读后校验——回执超 10 行即警告并要求重发三行版

**名实注**：回执代码块实为 4 行（含首尾包裹标记），「三行」指标记内内容行的历史习惯名——解析以标记配对为准，禁止按行数截取。

**判定生成规则（唯一权威——门禁类 agent 定义内嵌副本须与本节同步）**：

- **FAIL ⟺ 存在至少一条阻塞级发现**：adversarial-reviewer 的 High ｜ eng-validator 的 ERROR（数据验证档）｜ domain-guard 的 CONFIRMED
- 仅非阻塞级发现（Medium/PLAUSIBLE/WARNING/Low/OBSERVATION/INFO）或零发现 → **PASS**，判定行必须携带各级计数（H/M/L、C/P/O、E/W/I）交编排器裁量是否追加回炉——非阻塞发现不自动阻塞，但不可静默
- 过程不可完成（输入缺失/关键材料不可读）→ **DEGRADED**，与发现无关（未完成的审查视为未通过）

**回炉载荷规则**：FAIL 回炉时，编排器构造的回炉任务书必须包含①验证/审查报告路径②全部阻塞级发现条目原文（或首步指令=Read 该报告的『阻塞级发现』节）；非阻塞级发现只带计数不附原文——对齐反思记忆上限（1-3 条），防上下文灌爆。实证依据：带语言反馈的重试显著优于盲重试，盲重试不优于基线

## 4. 对抗审查环节

审查角色已随包分发（`agents/adversarial-reviewer.md`，第一步复制的 7 文件之一），即复制即用。两种取用方式：

- **优先**：直接用随包的 adversarial-reviewer（完整定义：先立后破三步流 + 专项必查 + 输出契约）；项目已有同名 agent 时优先项目版（同名双轨）
- **应急**：若目标环境缺失该文件，可临时用下面的最小定义存为 `.claude/agents/adversarial-reviewer.md`：

```markdown
---
name: adversarial-reviewer
description: "[审查] 对方案/设计文档做对抗审查：默认假设方案有缺陷，用证据说服自己它是对的。挑可执行性/安全性/完整性问题。"
model: opus
---
你是对抗审查员。立场：默认假设方案有缺陷，你的任务是**用证据说服自己它是对的**——说服不了，缺陷成立。
纪律：
1. 先立后破：先逐项实证核实方案做对的部分（Grep/行号复核成表），全部成立后才列发现——防全盘否定
2. 每条发现含：严重级（High/Medium/Low）+ 触发场景 + 证据锚 + 修复方向
3. 自反一致性必查：方案手段与方案批判目标是否自矛盾
4. 核查缺陷模式清单：知识漂移/静默失败/审计断链/契约冲突/窗口期风险（详见 methodology/review-patterns）
5. 不确定 → Grep/Read 核实，不要猜测
输出约定：详情落盘 + 极简三行（判定=PASS|FAIL|DEGRADED，FAIL 时含 H/M/L 计数）。
```

审查任务书要求（编排器构造任务书时必须包含）：方案全文路径 + 审查重点域 + 「先立后破」要求 + 红线域标注 + 输出落盘路径（expect 产物）。审查 agent **独占运行不并行**。

## 5. 档位分配原则

| 环节 | 档位 | 工具面 | 理由 |
|---|---|---|---|
| 侦查 | 轻 | Read,Glob,Grep,Write,Bash,WebFetch | 执行密集（跑命令/查询/搜索），判断骨架已由子模式定义 |
| 设计 | 重 | Read,Glob,Grep,Write,Bash | 判断密集（架构取舍/侵入点识别） |
| 对抗审查 | 重 | Read,Glob,Grep,Write | 判断密集（缺陷推理） |
| 红线域守卫 | 重 + 独占（重试高于常规） | Read,Glob,Grep,Write | 语义层审查，漏报代价最高 |
| 实施 | 轻 | 全量 | 规格已定，执行密集 |
| 交叉验证 | 重 | Read,Glob,Grep,Write | 逐条对照的判断密集（三分法归类） |
| 归档 | 轻 | Read,Write,Edit,Glob,Grep | 结构化操作 |

**工具面附注**：工具面=最小权限实现（门禁类无 Edit/Bash，Write 供报告落盘）；含 Bash 的工具面下，不改码约束仍由行为约定兜底（Bash 可写文件是已知妥协）；平台字段优先、行为约束兜底（非 Claude Code 宿主此字段无害）

兜底规则：不确定时默认不指定 model（继承主对话档），**不主动降轻档**。原则一句话：**判断密集环节升重档，执行密集环节降轻档**。

## 6. 分派对账机制（dispatch / done / expect / check）

解决「agent 静默死亡靠肉眼发现」（诞生背景：同 session 两类 agent 静默死——API 配额中断/审查 agent 无声退出）。

**协议**：四事件协议（dispatch 登记 / done 回执 / expect 判定 / check 扫描），JSONL 追加写（每 agent 派发一条），记录字段：`ts / event / agent / task / verdict / expect_file`（verdict 与 expect_file 按事件按需携带；done 事件另可携带可选计量字段 `tokens / duration_ms / tool_calls`——编排器从宿主回执读取，缺省不记）：

```json
{"ts": "2026-10-01T09:00:00", "event": "dispatch", "agent": "eng-recon", "task": "r1_tech", "expect_file": "results/exec-detail-x/r1_tech.md"}
{"ts": "2026-10-01T09:40:00", "event": "done", "agent": "eng-recon", "task": "r1_tech", "verdict": "DONE"}
```

- **dispatch**：真实派发后登记（先派发后登记——配合「禁止虚报状态」铁律）
- **done**：收到极简三行回执时登记
- **expect 判定**：**产物文件存在 = 自动视为完成**（比自觉回执强——完成判定锚产物存在性，不锚自述）
- **check**：扫描「有 dispatch 无 done 且 expect_file 不存在」的悬空条目 → 报警

**ledger 口径与计量扩展**：

- **每战役独立 ledger**：AGENT_LEDGER 按战役指定（如 `results/agent_ledger-<战役名>.jsonl`），收官 check 以本战役 ledger 为口径——防历史悬空成永久噪声
- **done 事件可选字段**扩 `tokens / duration_ms / tool_calls`（编排器从宿主回执读取；add() 加三个可选参数）
- **check 尾部输出本战役累计汇总**（若字段存在）

**最小实现**（纯标准库零依赖，幂等，坏行容错——可直接保存为项目脚本）：

```python
#!/usr/bin/env python3
"""agent_reconcile.py — 分派对账：dispatch/done 登记 + 悬空检测（v1.1 七处修复版）"""
import json, os, sys, argparse
from datetime import datetime
from pathlib import Path

# 账本路径：环境变量 AGENT_LEDGER 优先，未设则用默认值（可直接保存即用）
# 每战役独立 ledger：AGENT_LEDGER 按战役指定（如 results/agent_ledger-<战役名>.jsonl），
# 收官 check 以本战役 ledger 为口径——防历史悬空成永久噪声
LEDGER = Path(os.environ.get("AGENT_LEDGER", "results/agent_ledger.jsonl"))

def add(event, agent, task, verdict="", expect_file="",
        tokens=None, duration_ms=None, tool_calls=None):
    LEDGER.parent.mkdir(parents=True, exist_ok=True)
    # 修复④：微秒精度时间戳——STALE 判定的比较基准（兜手写秒精度行另加 1s 容差，见 check）
    rec = {"ts": datetime.now().isoformat(timespec="microseconds"), "event": event,
           "agent": agent, "task": task}
    if verdict: rec["verdict"] = verdict
    # 登记时即绝对路径化——消除 check 方 cwd 与登记方不一致导致的误报/漏报
    if expect_file: rec["expect_file"] = str(Path(expect_file).resolve())
    # done 可选计量字段（编排器从宿主回执读取，缺省不记）
    if tokens is not None: rec["tokens"] = tokens
    if duration_ms is not None: rec["duration_ms"] = duration_ms
    if tool_calls is not None: rec["tool_calls"] = tool_calls
    with LEDGER.open("a", encoding="utf-8") as f:
        f.write(json.dumps(rec, ensure_ascii=False) + "\n")
    # 修复①（配合③）：dispatch 对同键重复派发时本函数天然追加保留全部历史行，
    # 旧 done 的失效由 check 重放到最新 dispatch 行时 done.discard(key) 处理

def check():
    if not LEDGER.exists():  # 修复⑥：账本缺失是合法初态（无派发记录），不崩溃
        print("账本不存在（无派发记录）")
        return
    dispatched, done, agg = {}, set(), {}
    for line in LEDGER.read_text(encoding="utf-8").splitlines():
        try: rec = json.loads(line)
        except (json.JSONDecodeError, TypeError, KeyError, IndexError): continue  # 修复②：坏行容错四类异常
        if not isinstance(rec, dict): continue  # 修复②：JSON 标量/数组行容错
        ev = rec.get("event")  # 修复②：取键全部 .get() 化，不假设字段存在
        if ev == "dispatch":
            key = (rec.get("agent"), rec.get("task"))
            dispatched[key] = rec  # 同键覆盖=取最新 dispatch
            done.discard(key)  # 修复③：新派发使旧回执失效——防回炉后静默死亡被旧 done 掩盖
        elif ev == "done":
            key = (rec.get("agent"), rec.get("task"))
            done.add(key)
            for fld in ("tokens", "duration_ms", "tool_calls"):
                v = rec.get(fld)
                if isinstance(v, (int, float)): agg[fld] = agg.get(fld, 0) + v
    dangling, stale = [], []
    for key, rec in dispatched.items():
        if key in done: continue
        exp = rec.get("expect_file", "")
        if exp and Path(exp).exists():
            # 回炉防护：产物 mtime 早于本次 dispatch ts → 是上一轮旧产物（如首轮 FAIL 报告），
            # 当前派发已静默死亡——不能让旧产物冒充本次完成
            try: ts = datetime.fromisoformat(rec.get("ts")).timestamp()
            except (ValueError, TypeError):
                print("WARN: 无法解析 ts（疑似 Z 后缀旧版环境）——跳过该行 STALE 判定")  # 修复⑦
                ts = None
            if ts is not None and Path(exp).stat().st_mtime < ts + 1:
                # 修复④：+1s 容差向报警方向（fail-closed）——兜手写秒精度 ts 行的截断误差
                stale.append(key)
            continue
        dangling.append(key)
    if dangling or stale:
        if stale: print("STALE-EXPECT（expect 产物未更新于本次 dispatch 之后）:", ", ".join(f"{a}/{t}" for a, t in stale))  # 修复⑦：文案中性化
        if dangling: print("DANGLING:", ", ".join(f"{a}/{t}" for a, t in dangling))
    else:
        print("OK: no dangling dispatch")
    if agg:  # 本战役累计汇总（仅输出 ledger 中实际存在的计量字段）
        print("战役累计:", ", ".join(f"{k}={agg[k]}" for k in ("tokens", "duration_ms", "tool_calls") if k in agg))
    if dangling or stale: sys.exit(1)

if __name__ == "__main__":
    try: sys.stdout.reconfigure(encoding="utf-8")  # 修复⑤：Windows 控制台中文输出防乱码
    except AttributeError: pass  # 旧版 Python 无 reconfigure，退回默认编码
    p = argparse.ArgumentParser()
    p.add_argument("cmd", choices=["dispatch", "done", "check"])
    # 修复⑥：dispatch/done 必填 --agent/--task（check 免填）——防 None 值追加成坏行
    _req = len(sys.argv) > 1 and sys.argv[1] in ("dispatch", "done")
    p.add_argument("--agent", required=_req); p.add_argument("--task", required=_req)
    p.add_argument("--verdict", default=""); p.add_argument("--expect-file", default="")
    p.add_argument("--tokens", type=int, default=None)
    p.add_argument("--duration-ms", type=float, default=None)
    p.add_argument("--tool-calls", type=int, default=None)
    a = p.parse_args()
    if a.cmd == "check": check()
    else: add(a.cmd, a.agent, a.task, a.verdict, a.expect_file,
              tokens=a.tokens, duration_ms=a.duration_ms, tool_calls=a.tool_calls)
```

**联动**：check 可由监控/定时任务周期执行，悬空超阈值报警。注意：对**方案派发类**（无产物文件）任务，dispatch 不填 expect_file，依赖 done 回执——两类任务登记口径要一致，避免 check 误报。

**问题登记表**：战役目录下 `problems.md`（四列：级别 P0-P3 / 描述 / 处置 / 状态），编排者维护，可作为 expect_file 登记——§8 收官清单第 6 条「问题登记表收口」的收口对象。

**登记命令模板**（真实派发后立即执行）：

```bash
python agent_reconcile.py dispatch --agent <agent名> --task <任务ID> --expect-file <产物绝对路径>
python agent_reconcile.py done    --agent <agent名> --task <任务ID> --verdict <PASS|FAIL|DONE|DEGRADED>
python agent_reconcile.py check
```

**Claude Code 平台硬化（可选）**：SubagentStop hook 校验子 agent 退出的 final message 匹配 `[AGENT-OUTPUT-START]...[AGENT-OUTPUT-END]` 配对且 expect_file 已存在，不满足则 `decision: block` 打回——把悬空检测从周期扫描提前到退出瞬间。非硬依赖，无 hook 环境退回本节脚本扫描（平台字段优先、行为约束兜底）。

## 7. 并发纪律

- 轻环节并行按需派发，并行上限以项目 CLAUDE.md 集成段硬性规则 3 声明为准（本手册不自报数字；新环境先小规模实测再放开）
- 重档审查/验证/守卫环节**独占串行**——防审查质量被并发稀释
- 并行派发在同一个消息里发出（多 tool call 并行），便于跟踪
- **独占与可终止的折衷（Claude Code 操作语义）**：重档环节以 run_in_background=true 派发取 task_id（布防 TaskStop 能力），完成通知到达前不派发任何新 agent（语义独占）——机械独占原语与后台任务 id 在宿主中不可兼得时，以此折衷为准

## 8. 收官清单

**前置（长战役）**：每个门禁转换点顺手更新 problems.md 与 campaign.md 状态行（压缩后此二文件是唯一权威）。

1. 全部判定 PASS/DONE（对账 check 无悬空）
2. 文档归档完成（documenter）
3. **知识提炼判定**：Grep 战役核心症状词于 `.claude/skills/` 全域（含 drafts/ 与 methodology/，**排除 knowledge-capture/**——机制元文档非症状知识，防自指命中把加急常态化）——**命中判定以 frontmatter 与路由表行为先例，正文普通词命中不计**；命中 ≥1 即带 `sop_hint: true` 加急归档；**每次收官恒跑**轻扫兜底（命中战役同样可能有无症状词的可结构化结论）
4. 即时草稿（若有）在收官呈报中显式提及待采纳
5. drafts/ 日期机械锚：收官时列 drafts/ 文件名日期，超期草稿（阈值见维护规则）逐条呈报请裁决——「季度清理」外化为每次收官的机械日期判定，不依赖「记得季度这件事」的自觉
6. 问题登记表收口（P0 清零或显式呈报，P1/P2 已修已记，P3 已呈报；登记表定义见 §6）
7. **预算/选轨偏差**：战役开始声明的轨道与预算 vs 实际消耗——偏差显著一句话归因，为零显式记「一致」
8. **stale 扫描**：Grep 总索引「最后验证」列，超期条目（阈值见维护规则）呈报
9. **DoD 对照**：本战役实际消费过的 methodology skill，其验证清单逐项核对并在呈报带结论
10. **复查联动**：本战役改动域命中某 active 条目的触发词/适用边界 → 呈报标注该条目「建议复查」（人工裁决，不自动改状态）
