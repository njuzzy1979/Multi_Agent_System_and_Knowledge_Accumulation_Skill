## 第二部分：发现清单（四件套）

### High-1 并行上限的权威源构成「手册→集成段→维护规则」死循环，且集成段自报数字违反自身声明

- **严重级**：High
- **触发场景**：目标项目接入后，编排器需要确定轻环节并行上限。查手册 §7（六件套管线手册.md:160）——「并行上限以项目 CLAUDE.md 集成段硬性规则 3 声明为准」；查集成段硬性规则 3（CLAUDE.md集成段.md:24）——「轻环节并行上限按平台实测锚定（3-4 并行为已验证安全量级）」，但集成段头部（:3）自己声明「行数上限等数值**不在本段定义**——以知识库总索引 README 维护规则为唯一权威」；查维护规则八项（索引与路由模板.md:52-58）——**没有并行上限这一项**。三方指向构成 A→B→C 而 C 无此项的闭环断裂。
- **影响**：这正是本体系为根治「18 vs 10」而立的单一权威源规则（CLAUDE.md:43「行数/阈值等数值只在索引与路由模板.md 维护规则节定义一次，其余任何位置（README/集成段/agent 定义）单向引用不自报数字」）的活体复发：集成段自报了「3-4」，同时声明自己不自报；两个文件对「谁是权威」互相指向对方，权威位实际缺位。未来任何一处调整并行数字，另一处无从发现——与 18 vs 10 完全同型的契约冲突温床。
- **修复方向**：二选一。(a) 维护规则增第 9 项「轻环节并行上限」，集成段硬性规则 3 改为「并行上限见知识库总索引维护规则」纯引用；(b) 明文扩界：维护规则权威范围声明改为「索引/沉淀类数值」，管线运行类数值（并行/重试）权威位定在集成段，手册与维护规则的指向文字同步改。关键是三方指向链必须收敛到同一个实存位。

### High-2 对账脚本在「回炉后 re-dispatch」场景失效：旧 expect 文件残留使静默死亡检测归零

- **严重级**：High
- **触发场景**：eng-validator 首轮 FAIL（报告 `r5_validator.md` 已落盘，verdict=FAIL）→ 按设计回炉（手册:13「回炉｜门禁 FAIL 后退回上游环节返工」是高频常态事件）→ 编排器 re-dispatch 同名 task（expect_file 同路径）→ agent 静默死亡（API 配额中断——手册 §6:94 明言这正是该机制的诞生背景）→ 无 done 回执。跑 check：`dispatched[(validator, r5)]` 存在、不在 done 集，但 `Path(exp).exists()` 为真（旧 FAIL 报告还在）→ `continue` → 输出「OK: no dangling dispatch」。
- **影响**：机制的核心卖点（防 agent 静默死亡、完成判定锚产物存在性）在回炉场景系统性失效，且失效形态恰是体系自己最强的判例 1「rc=0 但 0 行」的结构同型——存在性锚点被旧产物满足，静默失败被「成功」覆盖。编排器可能基于假 OK 推进收官，或反复读到旧 FAIL 报告陷入回炉死循环烧预算。
- **修复方向**（设计层）：expect 判定加入时间维度——check 时比对 dispatch ts 与 expect 文件 mtime，「产物早于本次派发 → 视为悬空」；或规定 re-dispatch 必须 version 化 expect 路径（`r5_validator_v2.md`）或将旧产物先行归档改名。同时脚本对「同 (agent,task) 二次 dispatch」可显式告警提示核对旧产物。

### High-3 库内全部 4 个 SKILL.md 均缺元信息块——总纲自己违反自己定的「不可缺」规则，且无豁免声明

- **严重级**：High
- **触发场景**：按 CLAUDE.md:45（「元信息块四字段同构：每个 SKILL.md 尾部 `状态｜最后验证｜适用版本｜源材料` **不可缺**」）与 SKILL.md:73（「元信息块四字段同构（**索引可聚合的前提**）」）核对磁盘实际：Grep 全 skills/ 目录「^元信息｜状态=」，命中仅 SKILL.md:73 的规则定义本身与四模板.md 的 4 处模板行——knowledge-capture/SKILL.md、review-patterns、design-lessons、chain-audit 四个 SKILL.md **尾部全部没有元信息块**（均终于「验证清单」节）。
- **影响**：这四个文件复制进目标项目后就是初始库条目（README.md:42「冷启动可先以 methodology 三 skill + 判例精选开张」）。总索引地图表（索引与路由模板.md:33-35）要求每行有状态/最后验证/源材料列，而条目自身无块可聚合——「索引可聚合的前提」在开张第一天即落空，只能手工填表，恰是机制要防的「索引与条目漂移」。对照证据：references/README.md:11 为自己写了显式「meta 豁免」声明，说明设计者处理过登记表的自指，却未对 SKILL.md 做同样处理（既不补块、也不声明豁免）。体系批判「依赖自觉」，这条「不可缺」对自身文件无机械检查兜底。
- **修复方向**：给四个 SKILL.md 补元信息块（状态=active，最后验证=2026-10-01，适用版本=v1.1，源材料=转化自源体系实战）；或在 SKILL.md 写作规范节显式声明豁免范围（「knowledge-capture 总纲与 methodology 三 skill 为机制自带件，豁免元信息块，其状态由版本标记承载」）并同步修改 CLAUDE.md:45 的措辞。二选一，消除「规则说自己不可缺而自己缺」的自反矛盾。

### High-4 四模板生成器字段缺陷：模板二三四元信息缺「适用版本」，模板一状态枚举两档——与共通规则及三档定义冲突，将系统性遗传给全部未来转正条目

- **严重级**：High
- **触发场景**：任何一次草稿转正。执行者按四模板.md 模板二/三/四生成正文，模板尾行（:76、:103、:130）为「元信息：状态=<active\|draft> ｜ 最后验证=<YY-MM-DD> ｜ 源材料=<路径>」——**缺「适用版本」字段**（模板一 :46 四字段齐但状态枚举仅 `<active|draft>` 两档）。而共通规则 2（:138）声称「元信息块四类同构（状态/最后验证/适用版本/源材料）」，SKILL.md:73 与索引模板:37 定义状态**三档**（active|draft|stale）。
- **影响**：生成器与规则自相矛盾。所有按模板二三四产出的转正条目天然缺「适用版本」列 → 总索引地图表无法按统一列聚合（与 High-3 同根：聚合前提被破坏）；状态枚举两档使执行者无从得知 stale 态的存在与标法。契约冲突型缺陷在机制自己的生成器里复发。
- **修复方向**：模板二三四元信息行补「适用版本=<...>」占位；四个模板状态枚举统一为 `<active|draft|stale>`（或在模板旁注明「新条目初始填 active/draft，stale 由季度复查标打」，消除两档/三档口径差）。

### Medium-1 「门禁失败重试 1 次」两处自报、权威源无此项

- **严重级**：Medium
- **触发场景**：CLAUDE.md集成段.md:28（硬性规则 7）与六件套管线手册.md:37（铁律 4）各自写死「重试 1 次」；维护规则八项无重试次数。
- **影响**：重试次数是阈值类数值，两处定义、零权威位——若未来调整（如红线域重试 0 次直接熔断），两处漂移无从发现，与 18 vs 10 同型。
- **修复方向**：与 High-1 一并裁决归位（若走「管线运行类数值权威在集成段」路线，则手册 §2 铁律 4 改引用；若走「全部入维护规则」路线，则维护规则增项、集成段改引用）。

### Medium-2 「17 行」两处自报，权威源无此项，且与 drafts/README 模板实际行数不符

- **严重级**：Medium
- **触发场景**：索引与路由模板.md:100（§五标题「17 行即可启动」）与 README.md:42（「17 行规则即可」）两处自报同一数字；维护规则无「drafts README 行数」项。实数 §五 模板代码块内容约 8 行，「17 行」与实物不符。
- **影响**：行数数值双写无权威位；数字与模板实物脱节会让执行者困惑「17 行从哪数出来」。
- **修复方向**：删数字改定性（「drafts/README 模板即可启动」），或如实写「8 行」并归入维护规则。README.md:42 同步。

### Medium-3 判例诞生门槛「≥3」定义在 SKILL.md 正文，总纲自己打破「所有阈值只在维护规则定义」的总则

- **严重级**：Medium
- **触发场景**：SKILL.md:83 声称「所有行数/阈值数值只在总索引维护规则处定义一次，其余位置单向引用不自报数字」，但 SKILL.md:78 自定义「判例 ≥3 且步骤可复述」；索引与路由模板.md:134 的挖掘 prompt 反向指认「knowledge-capture SKILL.md Phase B 节」为权威位——体系中实际存在第二个数值权威位。
- **影响**：权威位分裂。当前数值仅一处定义（尚无漂移），但「唯一权威源=维护规则」的表述与事实不符，后续维护者会无所适从。
- **修复方向**：要么把「诞生门槛判例数 ≥3」挪进维护规则第 9 项、SKILL.md:78 改引用；要么把 SKILL.md:83 的总则改为「索引/行数/滚动类数值以维护规则为唯一权威；诞生门槛以本总纲 Phase B 节为权威」，并在维护规则加一行指回。

### Medium-4 轻扫兜底触发口径三处不一致：「每次收官固定」vs「零命中才跑」

- **严重级**：Medium
- **触发场景**：SKILL.md:49「恒跑轻扫兜底：**每次收官固定** ~1 分钟轻扫」；六件套管线手册.md:170（§8 清单 3）「命中 ≥1 即带 sop_hint: true 加急归档；**零命中跑**轻扫兜底」；CLAUDE.md集成段.md:48「**零命中时** documenter 恒跑轻扫兜底」（「恒跑」与条件化同句自相矛盾）。
- **影响**：命中 sop_hint 的战役到底还跑不跑轻扫，三个文件两种答案。按手册执行则命中战役可能遗漏非症状词类可结构化结论；按 SKILL.md 执行则多一次固定成本。行为不确定的规则等于没有规则。
- **修复方向**：统一为一种（建议：每次收官恒跑——它正是「提炼不退化为依赖自觉」的保底，命中战役同样可能有无症状词结论），手册 §8 与集成段措辞同步改。

### Medium-5 季度清理无机械锚：触发主体、触发方式、时序语义全部未定义

- **严重级**：Medium
- **触发场景**： drafts/ 内草稿超 90 天（索引与路由模板.md:53）。谁在什么时点执行清理？机制只写「季度复查：>90 天……清理（清理前收官步骤兜底重扫呈报）」——「季度复查」的执行者与触发器不存在；「清理**前**收官步骤兜底重扫」语义模糊（是每次收官都重扫待清理草稿，还是清理动作前的最后一次收官重扫？哪个收官知道自己是「清理前的收官」？）。
- **影响**：体系批判「依赖自觉必然失效」（判例 4：机械锚是「制度落到 LLM 行为学的关键发明」），而季度清理这个唯一的人口控制环节恰恰没有机械锚——草稿头部有 YYMMDD 日期可供机械判定，机制却没有写「收官时机械扫描 drafts/ 文件名日期」这个锚。失效后果是超期草稿无限堆积（不产生污染，产生冗余与呈报噪音）。
- **修复方向**：给收官清单增一条机械锚：「收官时列 drafts/ 文件名日期，超期（阈值见维护规则）草稿逐条呈报请裁决」——把「季度」外化为每次收官的日期机械判定，「季度清理」退化为呈报后的人工批量动作。

### Medium-6 收官扫描以 skills/ 全域为界，把 knowledge-capture 机制文档自身的元描述也当症状知识——sop_hint 加急判定在通用症状词下恒命中

- **严重级**：Medium
- **触发场景**：收官扫描「Grep 本战役核心症状词于知识库（含 drafts/）——命中 ≥1 即『第 2 次同类』→ sop_hint: true」（SKILL.md:48；集成段:48 同）。知识库=.claude/skills/ 全域（索引模板 §〇:10「不产生扫描盲区」）。knowledge-capture 自身的文档密集含机制元词：「根因/修复/复发/排除/反转」（SKILL.md:49）、「漂移/冲突」（review-patterns）。当战役核心症状词是半通用词（如「回滚」「缓存」「链路」「漂移」——真实战役常见），必命中机制文档或 methodology 文档。
- **影响**：methodology 命中是特性（真有同类 SOP）；但 knowledge-capture 机制文档的元命中是噪音——「第 2 次同类」判定失真，sop_hint 加急常态化（所有战役都加急 = 没有加急），documenter 必产草稿变成草稿噪音源。§〇 只考虑了漏报（盲区），没考虑元文档自命中的误报。零污染门禁兜底，故不升 High。
- **修复方向**：扫描范围显式排除 `knowledge-capture/`（机制文档非症状知识），或把「命中」的合格口径收窄为「命中条目来自地图表登记的领域 SOP 或 drafts/」；§〇 库边界规则补一句自指处理。

### Medium-7 草稿的 draft 警告不在「最先被读到的位置」——窗口期风险型缺陷自反复发

- **严重级**：Medium
- **触发场景**：索引与路由模板.md:98（§四）要求「draft 状态的 skill 行内自带警告——**状态警告放在最先被读到的位置**」、SKILL.md:70「draft 状态警告内置在 description（防窗口期风险）」。而四模板的草稿/转正条目结构：frontmatter description 只写「何时用：症状特征」无警告（四模板.md:21 等），状态标记在**文末**元信息块（:46/:76/:103/:130）。同时 Grep 兜底检索（索引模板:47-48「拿症状关键词直接 Grep 本目录」）以 skills/ 全域为界含 drafts/——检索命中草稿 → LLM Read → 最先读到的 description 无任何「未采纳勿采信」警告。
- **影响**：review-patterns 五类缺陷模式之一「窗口期风险型」（:23「draft/半配状态可被提前消费」）在本机制自己的草稿通道上复发：未采纳知识经 Grep 兜底进入消费视野，且最先读到的位置无门禁标记。这正是体系自我批判的病的复发形态。
- **修复方向**：四模板 frontmatter description 规范加一句「状态非 active 时，description 首句内置『draft——未采纳，仅供参考』」；或 drafts/ 草稿落盘时强制头部首行「> [draft 未采纳] ……」警告，转正时随 origin 字段一并处理。

### Medium-8 路由节行数上限「≤10 行」无计量口径，集成段实例自身卡线（内容行 10 / 含标题 11 / 含空行 13）

- **严重级**：Medium
- **触发场景**：维护规则 5（索引模板:55）「行数 ≤ <路由节上限，建议 10> 行」——未定义含不含标题、表头、空行。实测集成段路由节（CLAUDE.md集成段.md:31-44）：标题 1 + 引导 2 + 表头 2 + 数据 5 + 锚 1 = 内容 10 行，含标题 11 行，含空行 13 行。同一实例在不同口径下合规/超限两种结论。
- **影响**：行数上限是体系的核心机械规则之一，但计量单位不可机械判定——执行者各数各的，上限形同虚设的风险正是索引模板:91「供项目自查上限是否形同虚设」自己警惕的。附带：索引模板:91 的「实测口径（引导 2 行 + 指回 1 行 + 锚 2 行）」与 §三 模板实际固定开销（引导 4 行 + 锚 2 行，:75-79、:87-88）对不上。
- **修复方向**：维护规则 5 补计量定义（建议：「表体行数计，不含标题/空行，含表头」或「markdown 渲染行含空行」任选其一写死）；索引模板:91 的预算拆分按 §三 模板实测改准（引导 4 + 表头 2 + 锚 2 = 固定 8，表行预算 = 上限 − 8）。

### Medium-9 收官清单第 5 条「问题登记表收口」引用了从未定义出生地的实体

- **严重级**：Medium
- **触发场景**：手册 §8:172「问题登记表收口（P0 清零或显式呈报……）」。P0-P3 分级在集成段硬性规则 8（:29）定义，但「问题登记表」这个产物——建在哪个目录、什么格式、是否作为 expect_file 登记、由谁创建——全库无定义。
- **影响**：一个只看手册的执行者无法落地收官清单第 5 条；问题流转的终点实体悬空，P0-P3 分级失去承载物。
- **修复方向**：手册 §6 或集成段规则 8 补一句「问题登记表=战役目录下 problems.md（四列：级别/描述/处置/状态），作为编排者侧 expect 产物」。

### Medium-10 对账脚本 expect 相对路径的 cwd 约定只有注释声明，无机械防护

- **严重级**：Medium
- **触发场景**：脚本:130 注释「expect_file 一律记相对仓库根的路径，本脚本于仓库根执行（换 cwd 跑会使 exists() 全部误报悬空）」——约定存在但仅是注释。多 agent 环境中登记方（编排器/主对话的 Bash 调用）与检查方 cwd 可能不一致（本执行环境 Agent 线程的 cwd 在调用间即会重置）；登记时用了一个 cwd 基准的相对路径、check 时换了 cwd，则 exists() 全部失真——要么全悬空（误报），要么全通过（漏报，更危险）。
- **影响**：对账机制的可靠性系于一条无人强制执行的口头约定。
- **修复方向**：dispatch 登记时把 expect_file 解析为绝对路径存储（`Path(exp).resolve()`），或脚本启动时校验 cwd 含 LEDGER 父目录，否则拒绝执行并报错——把注释变成代码。

### Medium-11 集成段常驻约 60 行无总预算声明——判例 12 的防膨胀三件套只罩住了路由节

- **严重级**：Medium
- **触发场景**：六渠道表对 CLAUDE.md 的定位「每 session 加载，要省行数」（SKILL.md:16）；判例 12「知识库治主指令文件膨胀，自身设计必须内建防膨胀：行数上限+滚动淘汰+单一数值权威源」（实战判例精选.md:81）。集成段四节粘贴后常驻目标项目 CLAUDE.md 约 60 行，其中只有路由节受 ≤10 行上限约束，Agent 调用规则（表+8 条硬规则，约 28 行）、提炼规则、上下文声明三节无任何预算与约束。
- **影响**：可辩护处在这三节是机制常数、不随知识增长；但「省行数」原则对自身 60 行常驻无任何声明与预算上限，属于自反不彻底——防膨胀设计只覆盖了增长型内容，未对自己的一次性占用立规。后续版本迭代集成段时无刹车。
- **修复方向**：集成段头部声明总预算（如「四节合计 ≤70 行，超限先砍硬性规则表述再砍表」），或把该预算写入维护规则并在 CLAUDE.md 修改纪律中引用。

## 第三部分：机制合理性与可用性总评

**总体判定：DEGRADED——骨架优秀，自反合规未达标，4 项 High 修正前不宜宣称 v1.1「根治」了它批判的病。**

**做对的核心**：这套机制最值钱的设计——双索引分工与主从声明、机械锚（收 X 必做 Y）、人机边界宪法（LLM 只做机械抽取）、四模板按来源机械路由、库边界先于索引规则（§〇）、两级草稿辨析、判例驱动（每条反直觉规则带实证）——在交叉核对中表现出高内部一致性（21 项核实全过，机械锚模式串三处逐字一致）。单一权威源对 8 项阈值数值确实做到了全库唯一定义，18 vs 10 的教训被真实固化。

**自反必查的裁决**：这套机制治四个病——(1) 知识漂移：Medium-6/Medium-8/Low-7/Low-8 显示索引与计量细节存在漂移种子，但主锚点未漂；(2) 契约冲突：**High-1（并行上限权威死循环+自报）与 High-4（模板字段与共通规则冲突）是 18 vs 10 的活体复发**，恰发生在为根治它而立的规则体系内部；(3) 主指令文件膨胀：Medium-11 显示防膨胀三件套只罩住路由节，集成段自身 60 行常驻无预算；(4) 依赖自觉：Medium-5（季度清理无机械锚）与 High-3（「不可缺」规则对自身文件无机械兜底且实际全缺）是「批判自觉依赖的机制自己依赖自觉」的直接复发。四个病三个有复发实证——这不是骨架问题，是收尾打磨问题，但必须承认其存在。

**可用性**：三步接入可走通（路径引用链基本自洽、登记表与磁盘一致、冷启动豁免衔接闭环）；对账脚本在「首次派发」主路径上可用，但回炉 re-dispatch 场景（High-2）会静默失效——而回炉是设计内高频事件，建议接入者在使用前先打该补丁。四模板作为生成器，字段缺陷（High-4）会在首批转正条目上立即显形。

**建议处置**：High-1/2/3/4 修正后再版（工作量小：改数行文字+脚本 3 行）；Medium 项可载入已知限制随版发布；Low 项记录即可。修正后本机制有资格成为它自我期许的「组织知识沉淀基础设施」——当前的差距不在设计思想，在于最后一轮「按自己的规则审自己」没有被执行过。本次审计即是补上这一轮。
