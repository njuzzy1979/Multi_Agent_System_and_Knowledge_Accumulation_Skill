## 二、后破：发现清单

### H-1（High）四个 SKILL.md 全部缺失元信息块四字段——第三步建总索引时「状态/最后验证/源材料」列无值可填，且直接违反本仓库 CLAUDE.md 明文纪律

- **触发场景**：新用户完成第三步，按索引与路由模板 §二「总索引 README 模板（新建知识库时复制此节）」建 `.claude\skills\README.md`。地图表列为「skill 路径｜症状触发词｜模板类｜**状态**｜**最后验证**｜一句话用途｜**源材料**」——methodology 三 skill 是冷启动初始库成员（§七冷启动豁免明确以它们开张），但三个 SKILL.md 尾部只有 `---`，没有任何元信息。状态填 active 还是 draft？最后验证填哪天？源材料填什么？用户只能自行猜测， Guess 出的值因人而异——索引可聚合性（元信息块的设计目的）在接入第一天即失效。
- **证据锚**：
  - 规则侧：CLAUDE.md:45「**元信息块四字段同构**：每个 SKILL.md 尾部 `状态 | 最后验证 | 适用版本 | 源材料` **不可缺**」；knowledge-capture SKILL.md:73（写作规范）「元信息块四字段同构（索引可聚合的前提）」；四模板.md:138「保证总索引可按统一列聚合」。
  - 资产侧：review-patterns/SKILL.md:61、design-lessons/SKILL.md:62、chain-audit/SKILL.md:71、knowledge-capture/SKILL.md:100 —— 尾部均仅 `---`，全库 Grep「元信息：」只在四模板.md 模板行内命中，无一处实际落地。
  - 连带：CLAUDE.md:45 同时要求「文件头部的版本标记（`+ 版本 v1.1`）」，四个 SKILL.md 文件头部也全无版本标记——该纪律全库无一处可执行对象。
- **自反性说明**：这正是体系自己定义的「契约冲突型 + 知识漂移型」问题——治理纪律明文「不可缺」，被治理资产全缺。判例精选判例 12（治理机制自反一致）在此翻车。
- **修复方向**：给四个 SKILL.md 尾部补元信息行（参考值：状态=active、最后验证=2026-09（实战转化验证）、适用版本=v1.1、源材料=「先例引用」节所列源体系战役），并在文件头部补版本标记；或修改 CLAUDE.md:45 措辞，明确「元信息块要求针对目标项目转正条目，本仓库 SKILL.md 豁免」——二选一，消灭规则与资产的矛盾态。

### M-1（Medium）「本项目首批判例：<登记处>」占位全库无权威出处——首次知识沉淀必卡

- **触发场景**：目标项目沉淀第一条本项目判例时，用户/agent 读到 methodology 三 skill「先例引用」节的「本项目首批判例：<登记处>」——「登记处」是什么？往哪登记？填什么格式？全库 Grep「登记处」仅这三处出现（review-patterns:53、design-lessons:52、chain-audit:61），knowledge-capture 总纲、四模板、索引与路由模板均未定义。四模板.md:39-40 的先例引用节模板写法是「<版本号 / 战役报告路径 + 一句话结论>」，并无「首批判例」行的设计。这卡在体系的核心价值主张（知识沉淀闭环）的第一次执行上。
- **证据锚**：上述三行；CLAUDE.md:54 占位符清点规则只覆盖 `{{`（三文件）与「索引与路由模板的**数值**占位用 `<...>`」——`<登记处>` 是第三种用法（文本占位、非数值、非索引模板内），规则未覆盖，用户执行「占位符清点」自查时对它无所适从。
- **修复方向**：在 knowledge-capture SKILL.md 或四模板.md 补「先例引用节双行结构」定义（示例来源行 + 本项目判例行的登记位与格式）；或把 `<登记处>` 改为自说明写法（如「本项目判例：追加于本节，格式=<日期+报告路径+一句话>」）。

### M-2（Medium）domain-guard 实际 5 个占位符，README 第一步只枚举 3 个；{{DETERMINISTIC_LAYER}} 无「项目无第一道防线」时的填法

- **修复方向**：README 枚举补全为「红线域名/失败后果/检查项/影响单位/确定性防线」五项；domain-guard 的 {{DETERMINISTIC_LAYER}} 占位例示补「项目暂无第一道防线时写『无（仅本 agent 第二道防线）』」。

### M-3（Medium）四模板.md 模板二/三/四的元信息行缺「适用版本」字段，与自身共通规则「四类同构」矛盾

- **触发场景**：目标项目按模板二/三/四转正条目时，产出天然缺「适用版本」字段；总索引按统一列聚合时三类条目恒少一列——四模板.md:138 自称「元信息块四类同构（状态/最后验证/适用版本/源材料）——保证总索引可按统一列聚合」，而 :76 / :103 / :130 三个模板的元信息行实为三字段（无适用版本），仅 :46 模板一为四字段。规则与模板自相矛盾，又一个「契约冲突型」活例。
- **证据锚**：四模板.md:46 vs :76/:103/:130 vs :138。
- **修复方向**：模板二/三/四元信息行补「适用版本=<…>」；或把共通规则第 2 条改为「状态/最后验证/源材料三类同构，适用版本按需」，二选一。

### M-4（Medium）review-patterns:37「替身计数=N」领域残留未按判例引用红线标注「示例来源」

- **触发场景**：通用项目读者读到验证断言附则的示例「替身计数=N 且持续 M 个周期」——「替身」是源体系特定业务概念，通用语义不明且无来源标注。违反体系自己的成文红线：四模板.md:146「示例判例若来自其他项目（如源体系），标注『示例来源：<项目名>』」。全库 Grep 领域词（FAS/涨停/替身/账户/风控/下单/扣费/订单）后确认：这是唯一一处未带「示例来源」前缀或「例：」占位性质的领域残留。

**冷启动检索有效性**：三个典型症状词全域 Grep 全部命中目标 SKILL.md 与集成段路由行（先立 #9）——体系声称的 grep 兜底可检索性实测成立。

## 四、可用性结论

三步接入的**主干真实可走通**：文件数、路径、注册机制、复制后路径自洽、冷启动衔接、检索兜底全部实证为真，无一处虚假宣传。但按文档操作会在两个点卡住或被迫自行拍板：第三步建总索引时初始三 skill 的关键索引列无值可填（H-1，且与 CLAUDE.md 明文纪律冲突）；接入后首次知识沉淀时「登记处」占位无解释（M-1）。另有 domain-guard 填充清单不全（M-2）、四模板自称与模板实文矛盾（M-3）、一处未标注领域残留（M-4）。综合判定 **DEGRADED**：功能骨架可用，指定环节需人工补判断——恰是体系自己定义的「降级成功」态。修复 H-1 与 M-1 后可复评 PASS。
